# Large loads skip the previous range comparison

By default the dashboard does not fetch the previous range when the selected range, summed over the selected repositories, holds more than 500 merged PRs. The previous range serves only the change figures, yet fetching it roughly doubles the wait and the GitHub API usage, which hurts exactly the repositories that are already slow. The server decides, with the one-search count probe of ADR-0005, and a probe that fails also skips the comparison, because an unknown size must not cause a slow load. We rejected deciding per repository, because pooled values would then compare different sets of repositories, and counting the previous range too, because the decision should follow the range the user chose. The cost is that a big repository loses its change figures until the user chooses Always or a shorter range.
